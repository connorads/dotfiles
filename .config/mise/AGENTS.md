# mise, aube and `up`

Tool versions, the lockfile, the npm backend and the update pipeline. Package-manager quarantines outside mise: [docs/supply-chain.md](../../docs/supply-chain.md).

## Claude Code

Claude Code is mise-owned, not natively installed: `~/.local/share/claude/` and
its `~/.local/bin/claude` shim are absent, and `command -v claude` resolves
through mise. `DISABLE_UPDATES` in [`.claude/settings.json`](../../.claude/settings.json)'s
`env` block is what holds the self-updater off - deliberately Claude-scoped,
since the name is not namespaced and nothing outside Claude Code reads that
file. The binary patches that survive (computer-use, session-reaper, plus the
read-only commit-note check) are reapplied by the mise postinstall; `--channels`
is **not** patched, and the reasoning is
[docs/adr/0011](../../docs/adr/0011-claude-binary-is-not-patched-and-mise-owns-the-install.md).

## Quarantine, lockfile and ranges

Mise tools use a **4-day quarantine** (`minimum_release_age = "4d"`) - only versions released 4+ days ago are installed. This gives the community time to catch compromised releases. GitHub attestation and SLSA provenance verification are also enabled; `locked_verify_provenance = true` re-verifies provenance at install time even when the lockfile already has a checksum (otherwise skipped on lockfile hits).

**Lockfile** (`lockfile = true`, `lockfile_platforms = ["macos-arm64", "linux-arm64", "linux-x64"]`): the committed `~/.config/mise/mise.lock` pins exact versions **and** checksums per platform - the mise analogue of `flake.lock`. The quarantine gates *resolution time* but pins nothing; the lockfile makes every machine install the identical vetted artifact rather than independently re-resolving ranges. The current platform is always locked regardless; the three listed cover the Macs (`macos-arm64`), dev/rpi5 (`linux-arm64`), and penguin/codespaces (`linux-x64`). Complementary, not a replacement: keep `minimum_release_age` / excludes / attestation / slsa.

That promise is void whenever GitHub refuses mise's token, and nothing says so. `MISE_GITHUB_TOKEN` is a credential independent of `gh auth` - a working `gh` says nothing about it - and it appears nowhere in this repo, so it is injected from outside and its expiry is invisible here. When it is rejected, `mise upgrade` emits a `401 Unauthorized` WARN per API call and **still exits 0**, while every `github:`-backed tool keeps its old version and its old lockfile checksums. `up` reports that as a degradation on the `mise` row; without renewing the token the bump is a no-op for those tools.

**Version ranges, not "latest"**: tools are pinned to major or major.minor ranges (e.g., `deno = "2"`, `pkl = "0.31"`). `mise upgrade` pulls patches within the range; `--bump` crosses boundaries. Claude, Codex and Amp are exempted from quarantine via the `minimum_release_age_excludes` mise setting. Because `up` only ever runs `mise upgrade`, a range pin is a standing decision to stay on that major, and nothing prompts a revisit. The other failure mode is a versioning scheme whose leading component moves every release: `gcloud` increments its major weekly, so a range pin there is stale within a week, permanently - `latest` is the honest expression of the intent. `pin-audit`'s drift check is the counterweight, FLAGging every range the newest release has outgrown (deliberate holds excluded in `checks.ts`); acting on it stays manual.

**mise lockfile** (enabled): `~/.config/mise/mise.lock` pins exact versions + checksums for `macos-arm64`, `linux-arm64`, `linux-x64` (plus the current platform, always). Other-platform checksums are computed from registry metadata, with no download (cross-platform locking needs mise >= 2025.11.11, `lockfile_platforms` >= 2026.4.8). Caveat: those non-current-platform checksums are *recorded from metadata, not verified by download* here - but install-time `github_attestations` + `slsa` still fire on the machine that actually installs. `claude`/`codex`/`vercel` (among others) are `latest`, so their lock entries churn every `up` (no per-tool lock-exclude exists; accepted). `locked` is deliberately **off**: turning it on would fail closed when adding a new tool that isn't in the lockfile yet. Revisit `locked = true` once the toolset is stable.

## Python tooling

**Python tooling** (ruff / pyrefly / ty): `ruff = "0.16"` (registry-backed `aqua:astral-sh/ruff`) is the first-party lint + format gate (`ruff-check` / `ruff-format` hk steps, `mise run py-checks`). `"pipx:pyrefly" = "1"` is the typecheck gate for the three script dirs and handoff (`py-typecheck-*` hk steps); pipx backend (no aqua entry, mirrors `pipx:ty`) forwards the quarantine to uv's `--exclude-newer`. `pipx:ty = "0"` is kept for editor/LSP use only - pyrefly owns the gate. Every `pyrefly.toml` sets `preset = "strict"` (implicit-`Any` reporting on unannotated `dict`, untyped lambdas, empty containers) plus `unused-type-ignore` so stale suppressions fail; `all` is avoided because new error kinds land in minor releases at error severity. `py-typecheck.sh` passes `-c pyrefly.toml`: with no config found pyrefly falls back to the `basic` preset, which reports 0 errors on real type errors and exits 0, so a renamed or missing config must be a fatal error rather than a green gate. The mechanical-enforcement skill (`references/python.md`) keeps basedpyright as the default gate for typed projects; pyrefly is the pragmatic choice here because these are stdlib-only script dirs where its speed matters more than the idiom rules it lacks.

## `up`

**How `up` works**: by default it requires clean `mise.lock` and `flake.lock` files, then bumps and pathspec-commits each lock independently. `mise upgrade` stays within ranges and auto-locks every `lockfile_platforms` entry for each changed tool plus current-platform provenance, so no separate `mise lock` refresh is needed. A failed mise upgrade leaves its partial lock dirty and uncommitted for inspection. Brew/apt and `nfu` then run; `flake.lock` is committed only when both its update and every applicable rebuild succeed. Privileged hosts validate sudo before mutation and keep the ticket alive only for this invocation, so a headless run does not discover expired authentication at the rebuild. Independent phases continue after failure, report in the final summary, and make `up` exit 1; advisory checks report without failing the run. Unknown arguments exit 2 before any work. **`--frozen` / `-s` / `--skip-flake`** requires a clean committed `mise.lock`, installs it, skips standalone brew/apt and flake update/commit, then rebuilds. The macOS rebuild still runs Homebrew Bundle upgrades and declarative cleanup, including in frozen mode. The cleanup summary reports policy and phase outcomes without scanning reclaimable space or checking scheduler health. It permits a dirty `flake.lock` so `up -s` can retry a failed rebuild without bumping again. Do not use `up -s` after a failed mise upgrade; inspect and reconcile `.config/mise/mise.lock` first.

**Degradations**: a phase can exit 0 and still have done less than it claims - an expired GitHub token, a cleanup the OS refused. `up` scans each phase's own log slice for those markers and reports one inline on the phase's `Applied` row, with the remedy in `Next` and `- degraded, see Next` appended to the header line. The phase keeps its state and duration, and `up` still exits 0: the remedies need a human (a credential to renew, an OS permission to grant), so failing the run would leave it failing until someone acts. Markers today: GitHub API 401 and 403 (repo count, not warning count - one repo produces several warnings per run), and Homebrew's zap cleanup blocked by Full Disk Access. `pin-audit`'s FLAG count is *not* one - that phase worked correctly, so it enriches the `Advisories` row only.

On normal macOS runs, `up` runs `brew vulns --list-skipped` after activation if the standalone Brew phase was attempted, including after a failed update or rebuild. The scan covers installed formulae, including installed formula dependencies, but not casks or bundled libraries. Failed standalone Brew updates/upgrades also run `brew doctor`. Both native reports are advisory and cannot change update status or cleanup outcomes. `--no-audit` skips both vulnerability scans; doctor remains enabled. Frozen mode skips the Brew scan. The commands target Homebrew 7; unavailable checks warn.

```bash
up                                          # bump mise.lock + flake.lock + brew/apt, commit locks, rebuild
up -s / up --frozen                         # frozen: install clean committed mise.lock, permit dirty flake.lock retry; no bumps/standalone brew/apt/commit
mise upgrade --bump [tool]                  # cross version boundaries (still 4-day quarantine)
mise upgrade --bump --before 0d [tool]      # skip quarantine for urgent updates
mise outdated                               # available updates within ranges
mise outdated --bump                        # available updates beyond ranges
mise lock -g                                # refresh global lockfile checksums for all platforms
```

## aube

**aube** (primary npm backend for mise): config at `~/.config/aube/config.toml`. Set via mise: `npm.package_manager = "aube"`, which selects aube **embedded as a library** (mise >= 2026.7.15, [jdx/mise#11149](https://github.com/jdx/mise/pull/11149)); `aube_cli` selects shelling out to the CLI. So "aube the setting value" and "aube the command" are different things: the `aube` binary on `PATH` is the real CLI, pinned at 1.38.0, and it does not install mise's npm tools. Anything driving that CLI against a mise install dir is addressing a store the embedded library does not use - it brands the virtual store `node_modules/.mise` while the CLI looks for `.aube`, and silently drops the work at `tracing::debug!`. Layered defenses beyond a simple age gate:

- `minimumReleaseAge = 5760` (minutes - aube uses minutes, bun uses seconds, pnpm uses minutes, npm uses days)
- `minimumReleaseAgeStrict = true` - fail closed when no version satisfies the age gate. aube's default is advisory (silently falls back to the next-oldest satisfying version), unlike pnpm where strict is the default
- `minimumReleaseAgeExclude = ["@ampcode/*"]` - Amp publishes several times a day; keep the age gate for everything else
- `advisoryBloomCheck = "on"` - ~380KB bloom-filter prefilter for OSV `MAL-*` advisories on lockfile installs (~0.1% FPR, ~1 round-trip per typical install)
- `trustPolicy = "no-downgrade"` (default) - fails install if a package's trust evidence weakens, e.g. a version without the SLSA provenance its predecessor had. A real case: `@mariozechner/clipboard-*` platform packages shipped 0.3.3 without provenance while the root package kept it, same publisher and npm signing key. The fix for such a false positive is a `trustPolicyExclude` entry, removed once upstream restores attestations
- `lowDownloadThreshold = 1000` (default) - refuses packages with <1000 weekly downloads as typosquat defense. Niche-but-trusted tools listed in `allowedUnpopularPackages`
- similar-name check (default, aube >= 1.38) - refuses a package whose name is within a small edit distance of a top-100,000 npm name (`ERR_AUBE_SIMILAR_PACKAGE_NAME`). Interactive it prompts `y/N`; **non-TTY it is a hard refusal**, and mise drives the embedded aube with no TTY - so a false positive fails `up` closed
- `minimumPackageAge` (default 30 days) - aube's slopsquat defence on newly *registered names*, complementing `minimumReleaseAge`, which only ages *versions* of names that already exist
- `allowedUnpopularPackages` is one list feeding **three** gates: a match skips the similar-name, package-age and low-download checks alike (the OSV malicious-package check is unaffected). Current name-similarity false positives, verified out-of-band before listing - both are well over the download threshold, the short name is the whole problem: `cf` (the Cloudflare CLI, wrangler's publishing set, resembles `co` at distance 1) and `hunkdiff` (`modem-dev/hunk`, resembles `unidiff` at distance 2). Neither has provenance at the installed version *or* its predecessor, so `trustPolicy = no-downgrade` sees no weakening. `@eraserlabs/*` is the other shape: a genuinely new, genuinely unpopular package (~16 downloads/week, first published 2026-08-19) that trips the download **and** package-age gates at once, so the entry is what lets it install at all. Listed only after auditing the shipped tarballs of all seven packages - registry integrity matched, no install hooks, no telemetry, one egress host
- `allowBuilds = {}` (default empty) - lifecycle scripts blocked unless explicitly allowed via `aube approve-builds <pkg>` or `allowBuilds.pkg = true`. For a **mise** npm tool the approval belongs in `config.toml` instead, as the per-tool `allow_builds` list (`"npm:@tobilu/qmd" = { version = "2", allow_builds = [...] }`): mise sets `ignore_scripts` from its absence, so a tool with no `allow_builds` runs no dependency build script at all. The list is matched against every package in the resolved graph, so it reaches transitive deps, and the builds run during `mise install` itself

Settings routing: aube reads both `~/.npmrc` (npm-shared keys) and `~/.config/aube/config.toml` (aube-only keys). Keep aube-specific keys in the latter to avoid npm warnings ("Unknown user config 'minimum-release-age'") when mise calls `npm view` for metadata. CLI: `aube config set <key> <value>` routes correctly.

**Rule: aube keys live in `~/.config/aube/config.toml` only, never spelled into `~/.npmrc`.** On mise >= 2026.8.14 the per-install config lives at `<install>/.config/aube/config.toml` and sits **below** `userNpmrc` in aube's precedence order, so an aube-spelled key in `~/.npmrc` would silently override the per-install settings for every npm-backed tool. The two files are not interchangeable and the precedence is not the one you would guess.

Disk reclaim: `cleanup`'s `aube` target flushes only the regenerable cache `~/.cache/aube/packuments-full-v1` (plus `aube cache prune --age-days 0`). `~/.cache/aube/virtual-store` is preserved: it is live working set for the 156 installs still on the shared-store layout, and removing it dangles every `npm:*` tool bin symlinked into it. It never touches the durable CAS at `~/.local/share/aube/store`, nor `~/.cache/aube/primer` / `adaptive-state.json`. An install made by the embedded library keeps its store **per-install** at `<install>/node_modules/.mise` instead, so it is bulk inside the install dir rather than in the shared cache - part of the install, not something to sweep.

## Version-coupled tool pairs

**Version-coupled tool pairs**: `oxlint` and `npm:oxlint-tsgolint` are pinned separately, `up` bumps them separately, and tsgolint's version line tracks typescript-go rather than oxlint - oxlint 1.80.0 peers `oxlint-tsgolint >= 7.0.2001`, so the two majors will never agree and neither range constrains the other. A skew there does not fail loudly; it turns the type-aware rules off. `pin-audit` is the counterweight for the range-drift half of this, but the peer relationship itself is not machine-checked - check it by hand after either tool crosses a major.

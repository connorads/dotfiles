right, deploy fix is shipped. background: `pnpm deploy` was `build && wrangler deploy` - it never touched the database. applying migrations to remote D1 was a separate manual step you had to remember, and we stopped remembering: migrations 0007-0010 were in the code but had never been applied to prod, so the deployed worker was querying a schema that didn't exist. the table rename in 0010 made it fatal - live code selected FROM invitation (the renamed data table) while remote still had invitation as the old join table, so every admin.overview call threw and came back as an opaque 500. the whole admin dashboard was down and nobody noticed until i opened a page by hand.

fix: `pnpm deploy` is now `build && wrangler d1 migrations apply DB --remote && wrangler deploy`. build first so a compile error fails before we touch the prod db, migrate before deploy so new code meets the schema it expects. if migrate fails, deploy doesn't run and old code keeps serving the old schema, which is at least consistent.

i did think about moving deploys into CI on merge to main, which is honestly the more robust answer and also closes the hole this leaves (someone running a raw `wrangler deploy` bypasses the whole thing) - parked it because it needs a cloudflare api token in repo secrets and retires the one-command manual deploy, and right now it is literally just me deploying off one laptop. also considered having the worker check a schema version at boot and refuse to serve instead of throwing a cryptic 500 - didn't like it, it's a permanent obligation to bump a version marker on every single migration or the check quietly lies.

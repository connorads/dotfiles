the confirm flow has been dead in production and we finally know why. ADR 0002 has plans stored in the MCP session's Durable Object, which assumed propose and confirm share a session. on the host that's just false - it re-initialises a fresh MCP session, so a fresh session DO, for basically every tool call, so confirm_write always landed in a DO that had never seen the plan. telemetry proved it rather than us guessing: every real confirm attempt completed in 19-35ms with plan_not_found and zero upstream traffic, and we had never once emitted a write_plan_executed audit event.

so: plans now live one-per-plan in a dedicated WritePlanStore DO namespace, addressed by idFromName(sha256(confirmToken)). possession of the token is still the lookup capability exactly as before, the digest just keeps the raw secret out of DO names. a named DO is a single global strongly-consistent instance so any session holding the token reaches the same plan, and DO input gates preserve the pessimistic spend-the-token-before-replay single-use guarantee - two racing confirms deterministically give one execution and one plan_already_used. an alarm set at propose time deletes the object an hour after expiry.

we looked at a per-user DO but GrantProps carries no stable user identity (the logged user_id is a bearer-token hash that rotates with the token), so minting one means consent-flow changes for no property this doesn't already give us. and we looked at putting plans in KV, which survives session churn fine, but KV is eventually consistent with no atomic read-modify-write, so single-use consume degrades to best-effort - which is the one guarantee the whole confirm path exists to enforce.

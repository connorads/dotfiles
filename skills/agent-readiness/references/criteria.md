# Criteria

Generated by `scripts/probe.py --criteria-md` from the probe's registry. Do not edit by hand.

Criteria judge outcomes, never tools. Each outcome says what must be true. The examples are
some ways to get there, not requirements: any mechanism that makes the outcome true passes, and
no repo is marked down for choosing a different tool.

Columns: `method` is `probe` (decided by the script), `judge` (the agent decides from the cited
files) or `env` (needs forge access; skipped as `environment` without it). `approval` means
checking it runs commands, so ask first. `extension` marks criteria outside the 84-criterion
core catalogue; they count toward the gated level but not the flat score.

## Level 1

### `env_template` Environment Template

Tags: `repository`, `dev_env`, `judge`, `skippable`.

Every environment variable the app needs is listed with a safe example value, so an agent can run it without guessing.

Examples: `.env.example`, an env var table in README or AGENTS.md.

### `readme` README File

Tags: `repository`, `docs`, `probe`.

A root README says what the project is and how to set it up and use it.

Examples: `README.md`.

### `gitignore_comprehensive` Gitignore Comprehensive

Tags: `repository`, `security`, `probe`.

Git ignores local secrets and generated output for every stack in the repo, so a broad `git add` cannot commit them.

Examples: `.env`, `node_modules/`, `__pycache__/`, `target/`, `build/`.

### `formatter` Code Formatter

Tags: `application`, `style`, `probe`.

Formatting is automated, so style never needs a human decision and diffs stay about behaviour.

Examples: Prettier, oxfmt, Biome, ruff format, Black, gofmt, rustfmt, Spotless.

### `lint_config` Linter Configuration

Tags: `application`, `style`, `probe`.

A linter or static analyser is configured, so an agent learns about code-quality mistakes from a command rather than a reviewer.

Examples: ESLint, oxlint, Biome, ruff, golangci-lint, clippy, Checkstyle, SonarQube.

### `type_check` Type Checker

Tags: `application`, `style`, `probe`.

Types are checked statically: a type checker is configured, or the language's normal build compiles with types.

Examples: `tsconfig.json`, mypy, pyright, pyrefly, javac via Maven/Gradle, go build, cargo check.

### `unit_tests_exist` Unit Tests Exist

Tags: `application`, `testing`, `probe`.

The code has unit tests an agent can extend next to the code it changes.

Examples: `*.test.ts`, `__tests__/`, `tests/test_*.py`, `*_test.go`, `src/test/java`, `*.bats`.

## Level 2

### `automated_pr_review` Automated PR Review Generation

Tags: `repository`, `build`, `env`, `skippable`.

Automation writes review comments on pull requests, beyond pass/fail status checks.

Examples: claude-code-action, CodeRabbit, Danger, reviewdog.

### `build_cmd_doc` Build Command Documentation

Tags: `repository`, `build`, `probe`.

The docs give the command that builds or installs the project, or say plainly that there is no build step.

Examples: `pnpm build`, `uv sync`, `cargo build`, `./gradlew build`, `make`.

### `deps_pinned` Dependencies Pinned

Tags: `repository`, `build`, `probe`, `skippable`.

Every dependency manifest has a committed lockfile or exact pins, so two machines resolve the same versions.

Examples: `pnpm-lock.yaml`, `bun.lock`, `uv.lock`, `Cargo.lock`, `go.sum`, Gradle locking, Maven BOM with wrapper.

### `monorepo_tooling` Monorepo Tooling

Tags: `repository`, `build`, `probe`, `skippable`.

A repo with several packages declares them as a workspace, so boundaries and task order are explicit.

Examples: pnpm workspaces, Turborepo, Nx, `go.work`, Cargo workspace, Gradle multi-project, Bazel.

### `vcs_cli_tools` VCS CLI Tools

Tags: `repository`, `build`, `env`, `skippable`.

A forge CLI is installed and signed in where the agent runs. This describes the machine, not the repo.

Examples: gh auth status, glab auth status.

### `error_tracking_contextualized` Error Tracking Contextualized

Tags: `application`, `debugging`, `probe`.

Production errors reach an error tracker with stack traces and context that map back to code.

Examples: Sentry, Bugsnag, Rollbar, Honeybadger.

### `runbooks_documented` Runbooks Documented

Tags: `repository`, `debugging`, `probe`.

Incident procedures exist, in the repo or linked from it.

Examples: `runbooks/`, a link to a wiki runbook, on-call docs.

### `structured_logging` Structured Logging

Tags: `application`, `debugging`, `probe`.

Logs go through a logging library or one logger module, not scattered prints, so output can be filtered and parsed.

Examples: pino, winston, structlog, loguru, zap, slog, tracing, logback.

### `database_schema` Database Schema

Tags: `application`, `dev_env`, `probe`, `skippable`.

The data model is readable from the repo as a schema, models or migrations.

Examples: `schema.prisma`, `migrations/`, SQLAlchemy models, Drizzle schema, `schema.rb`.

### `devcontainer` Dev Container

Tags: `repository`, `dev_env`, `probe`.

The development environment is declared in the repo, so an agent can get a working shell without a setup session.

Examples: `.devcontainer/devcontainer.json`, flake.nix devShell, `devbox.json`, `.gitpod.yml`.

### `local_services_setup` Local Services Setup

Tags: `repository`, `dev_env`, `probe`, `skippable`.

Databases, caches and queues the code depends on can be started locally from checked-in config or clear docs.

Examples: `docker-compose.yml`, `compose.yaml`, devbox services, Tilt.

### `toolchain_pinned` Toolchain Pinned

Tags: `repository`, `dev_env`, `probe`, `extension`.

Runtime and tool versions are declared in the repo, so a fresh machine or sandbox gets the same compiler and runtime as the author.

Examples: `mise.toml`, `.tool-versions`, `flake.nix`, `devbox.json`, `.nvmrc`, `.python-version`, `rust-toolchain.toml`, go.mod toolchain, Gradle/Maven wrapper, volta.

### `agents_md` AGENTS.md File

Tags: `repository`, `docs`, `probe`.

A root agent instructions file gives setup, build, test and project conventions in more than a stub.

Examples: `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `.github/copilot-instructions.md`.

### `automated_doc_generation` Automated Documentation Generation

Tags: `repository`, `docs`, `probe`.

Some docs are generated or published from source, so they cannot drift from it silently.

Examples: TypeDoc, Sphinx, MkDocs, Javadoc, OpenAPI generators, git-cliff.

### `automated_security_review` Automated Security Review Generation

Tags: `repository`, `security`, `env`, `skippable`.

Automation produces readable security findings for changes, such as SAST results or dependency audit reports.

Examples: CodeQL, Semgrep, Snyk, osv-scanner, zizmor, Trivy.

### `branch_protection` Branch Protection

Tags: `repository`, `security`, `env`, `skippable`.

The default branch rejects direct pushes and requires review. Readable only through the forge API with admin rights.

Examples: GitHub rulesets, legacy branch protection, GitLab protected branches.

### `codeowners` CODEOWNERS File

Tags: `repository`, `security`, `probe`.

A CODEOWNERS file maps paths to reviewers, so agent changes reach the right person.

Examples: CODEOWNERS, `.github/CODEOWNERS`.

### `dependency_update_automation` Dependency Update Automation

Tags: `repository`, `security`, `probe`.

A bot proposes dependency updates, so versions do not rot unnoticed.

Examples: Dependabot, Renovate.

### `secrets_management` Secrets Management

Tags: `repository`, `security`, `probe`.

Secrets live outside the code, in CI secrets, a secret manager or encrypted files, and none are tracked in git.

Examples: CI secrets, SOPS, Vault, cloud secret managers, .env.example with .env ignored.

### `pre_commit_hooks` Pre-commit Hooks

Tags: `application`, `style`, `probe`.

Quality checks run locally before code leaves the machine. Any mechanism counts; checks that only run in CI do not.

Examples: husky, pre-commit, lefthook, hk, .githooks/ scripts, agent edit hooks that run lint or tests.

### `strict_typing` Strict Typing

Tags: `application`, `style`, `probe`, `skippable`.

Where the type checker has a stricter mode, it is on.

Examples: tsconfig "strict": true, mypy strict, pyright strict, pyrefly preset = "strict".

### `issue_labeling_system` Issue Labeling System

Tags: `repository`, `task_discovery`, `env`.

Issues carry consistent labels for type, priority and area, so work can be filtered by query.

Examples: `.github/labels.yml`, labeler config, labels on the forge.

### `issue_templates` Issue Templates

Tags: `repository`, `task_discovery`, `probe`.

Issue templates tell a reporter, human or agent, what information a bug or feature request needs.

Examples: `.github/ISSUE_TEMPLATE/`, `.gitlab/issue_templates/`.

### `pr_templates` PR Templates

Tags: `repository`, `task_discovery`, `probe`.

A pull request template asks for the change, how it was tested, and context for reviewers.

Examples: `.github/pull_request_template.md`, `.gitlab/merge_request_templates/`.

### `interactive_qa_exists` Interactive QA Exists

Tags: `application`, `testing`, `judge`.

The docs give an agent a complete path to run the app and drive one real interaction: dependencies, login handling, launch and the interaction itself. Reading only; nothing is run.

Examples: AGENTS.md run section, Playwright harness, curl against a health endpoint, a QA skill.

### `test_coverage_thresholds` Test Coverage Thresholds

Tags: `application`, `testing`, `probe`.

A minimum coverage level is enforced, so an agent knows a change that drops coverage will fail.

Examples: vitest thresholds, jest coverageThreshold, --cov-fail-under, JaCoCo check, Codecov target.

### `unit_tests_runnable` Unit Tests Runnable

Tags: `application`, `testing`, `judge`, `skippable`, `approval`.

Tests load and run locally. Verified with the runner's list or collect mode on one file, never the whole suite, and only with approval.

Examples: vitest list, jest --listTests, `pytest --collect-only <file>`, go test -list, cargo test --no-run.

## Level 3

### `agentic_development` Agentic Development

Tags: `repository`, `build`, `probe`.

Agents already take part in development: agent co-authored commits, agent config or skills in the repo, or CI that invokes an agent. Dependency bots do not count.

Examples: Co-authored-by: Claude, `.claude/`, `.agents/`, claude-code-action, codex exec in CI.

### `dead_feature_flag_detection` Dead Feature Flag Detection

Tags: `repository`, `build`, `probe`, `skippable`.

Stale feature flags are found and removed, by tooling or a written cleanup process.

Examples: ld-find-code-refs, a flag audit script, a documented flag lifecycle.

### `release_automation` Release Automation

Tags: `repository`, `build`, `probe`.

Releases or deploys happen from automation, not by hand.

Examples: deploy on merge, semantic-release, release-please, GoReleaser, Argo CD, Flux.

### `release_notes_automation` Release Notes Automation

Tags: `repository`, `build`, `probe`.

Release notes or a changelog are generated, on each release or on a schedule.

Examples: changesets, release-please, semantic-release, git-cliff, GitHub generated notes.

### `single_command_setup` Single Command Setup

Tags: `repository`, `build`, `judge`.

One command, or a short documented sequence, takes a fresh clone to a running dev target.

Examples: `make dev`, `pnpm install && pnpm dev`, `mise run setup`, `nix develop`, `./gradlew bootRun`.

### `unused_dependencies_detection` Unused Dependencies Detection

Tags: `application`, `build`, `probe`.

A tool flags declared dependencies the code does not use.

Examples: knip, depcheck, deptry, cargo-machete, go mod tidy in CI.

### `version_drift_detection` Version Drift Detection

Tags: `repository`, `build`, `probe`, `skippable`.

In a multi-package repo, something checks that packages agree on shared dependency versions.

Examples: syncpack, manypkg, sherif, pnpm catalogs, Gradle version catalog with enforcement.

### `alerting_configured` Alerting Configured

Tags: `application`, `debugging`, `probe`.

Alert rules or a paging integration notify people when the system misbehaves.

Examples: PagerDuty, Opsgenie, Alertmanager rules, Grafana alerting.

### `distributed_tracing` Distributed Tracing

Tags: `application`, `debugging`, `probe`.

A trace or request ID follows a request through the system, so one failure can be followed across services.

Examples: OpenTelemetry, X-Request-ID, Micrometer Tracing, dd-trace.

### `health_checks` Health Checks

Tags: `application`, `debugging`, `probe`, `skippable`.

A deployed service exposes health, liveness or readiness checks.

Examples: `/healthz`, Docker HEALTHCHECK, Kubernetes probes, Actuator health.

### `metrics_collection` Metrics Collection

Tags: `application`, `debugging`, `probe`.

The app emits runtime metrics, so the effect of a change on performance is measurable.

Examples: Prometheus client, StatsD, OpenTelemetry metrics, Datadog, Actuator.

### `devcontainer_runnable` Devcontainer Runnable

Tags: `repository`, `dev_env`, `judge`, `skippable`, `approval`.

The declared dev environment actually builds and starts. Checked only with approval.

Examples: devcontainer up, nix develop -c true, devbox run true.

### `api_schema_docs` API Schema Docs

Tags: `application`, `docs`, `probe`, `skippable`.

A service's API has a machine-readable schema.

Examples: `openapi.yaml`, `schema.graphql`, `*.proto`, FastAPI generated OpenAPI.

### `documentation_freshness` Documentation Freshness

Tags: `repository`, `docs`, `probe`.

At least one key doc (README, AGENTS.md, CLAUDE.md, CONTRIBUTING.md) changed in the last 180 days.

Examples: git log dates.

### `service_flow_documented` Service Architecture Documented

Tags: `repository`, `docs`, `probe`.

Architecture is written down: a diagram, or docs naming the services, APIs and databases the code talks to.

Examples: Mermaid, PlantUML, `ARCHITECTURE.md`, C4 diagrams.

### `skills` Skills Configuration

Tags: `repository`, `docs`, `probe`.

The repo ships at least one agent skill: a SKILL.md with name and description frontmatter and a real body.

Examples: `.agents/skills/<name>/SKILL.md`, `.claude/skills/`, `.codex/skills/`.

### `product_analytics_instrumentation` Product Analytics Instrumentation

Tags: `application`, `product`, `probe`.

Product usage is instrumented, so the effect of a change on users is measurable.

Examples: PostHog, Amplitude, Mixpanel, Segment, GA4.

### `log_scrubbing` Sensitive Data Log Scrubbing

Tags: `application`, `security`, `probe`.

Sensitive values are redacted before they reach logs.

Examples: pino redact, structlog processors, Logback masking, a redact utility.

### `min_release_age` Minimum Dependency Release Age

Tags: `repository`, `security`, `probe`.

New dependency releases wait a set number of days before adoption. Centralised updates or provenance checks alone do not count.

Examples: pnpm minimumReleaseAge, npm min-release-age, uv exclude-newer, Renovate minimumReleaseAge, Dependabot cooldown, bunfig minimumReleaseAge, Yarn npmMinimalAgeGate.

### `pii_handling` PII Handling

Tags: `application`, `security`, `judge`, `skippable`.

Personal data is identified and handled deliberately: detection, masking, synthetic test data or written rules.

Examples: Presidio, faker test data, a data-handling section in AGENTS.md.

### `secret_scanning` Secret Scanning

Tags: `repository`, `security`, `env`, `skippable`.

Commits are scanned for secrets, locally, in CI or by the forge.

Examples: gitleaks, trufflehog, detect-secrets, forge-native secret scanning.

### `dead_code_detection` Dead Code Detection

Tags: `application`, `style`, `probe`.

A tool flags unused exports, modules or functions.

Examples: knip, ts-prune, vulture, staticcheck, deadnix, noUnusedLocals.

### `duplicate_code_detection` Duplicate Code Detection

Tags: `application`, `style`, `probe`.

A tool flags copy-pasted code.

Examples: jscpd, PMD CPD, pylint duplicate-code, SonarQube.

### `large_file_detection` Large File Detection

Tags: `repository`, `style`, `probe`.

Something flags oversized files before they land: a hook, a lint rule, a CI job or LFS.

Examples: check-added-large-files, ESLint max-lines, pylint max-module-lines, Git LFS.

### `naming_consistency` Naming Consistency

Tags: `application`, `style`, `probe`.

Naming conventions are enforced by a lint rule or written down where agents read them.

Examples: `@typescript-eslint/naming-convention`, ruff N rules, pylint invalid-name, a naming section in AGENTS.md.

### `tech_debt_tracking` Technical Debt Tracking

Tags: `repository`, `style`, `probe`.

TODO and FIXME markers are tracked, by a scanner or a rule that links each to an issue.

Examples: eslint no-warning-comments, ruff TD/FIX rules, todo-to-issue, SonarQube.

### `integration_tests_exist` Integration Tests Exist

Tags: `application`, `testing`, `probe`.

Tests exercise components together or end to end, not only units in isolation.

Examples: Playwright, Cypress, `tests/integration/`, Testcontainers, `*IT.java`, bats CLI tests.

### `interactive_qa_runnable` Interactive QA Runnable

Tags: `application`, `testing`, `judge`, `approval`.

An agent can actually follow the QA path and drive the running app. Checked only with approval; falls back to judging the path's completeness.

Examples: Playwright session, a TUI driven in a PTY, curl returning 2xx.

### `test_naming_conventions` Test File Naming Conventions

Tags: `application`, `testing`, `probe`.

Test file names follow a pattern the runner is configured with or the docs state.

Examples: vitest include, jest testMatch, pytest python_files, `*_test.go`.

## Level 4

### `build_performance_tracking` Build Performance Tracking

Tags: `repository`, `build`, `env`, `skippable`.

Build time is watched and worked on: caching, build scans or exported timings.

Examples: Turborepo cache, Nx cache, Gradle build cache, `actions/cache`, Develocity.

### `deployment_frequency` Deployment Frequency

Tags: `repository`, `build`, `env`, `skippable`.

The system ships several times a week through automation. Needs release or run history from the forge.

Examples: gh release list, deploy workflow runs.

### `fast_ci_feedback` Fast CI Feedback

Tags: `repository`, `build`, `env`, `skippable`.

Typical pull request CI finishes in under ten minutes. Needs run history from the forge.

Examples: gh pr checks timing.

### `feature_flag_infrastructure` Feature Flag Infrastructure

Tags: `repository`, `build`, `probe`.

Changes can ship behind a runtime toggle.

Examples: LaunchDarkly, Statsig, Unleash, GrowthBook, OpenFeature, a flags module.

### `heavy_dependency_detection` Heavy Dependency Detection

Tags: `application`, `build`, `probe`, `skippable`.

A bundled app measures bundle size or enforces a budget.

Examples: size-limit, bundlewatch, webpack-bundle-analyzer, Lighthouse CI.

### `progressive_rollout` Progressive Rollout

Tags: `repository`, `build`, `probe`, `skippable`.

Deploys reach a slice of traffic first (canary, percentage or rings).

Examples: Argo Rollouts, Flagger, canary deploys, traffic splitting.

### `rollback_automation` Rollback Automation

Tags: `repository`, `build`, `probe`, `skippable`.

A bad deploy can be reverted with one documented action or automatically.

Examples: rollback workflow, helm rollback, argo rollback, documented one-step revert.

### `circuit_breakers` Circuit Breakers

Tags: `application`, `debugging`, `probe`, `skippable`.

Calls to external services fail fast and retry with backoff instead of cascading.

Examples: opossum, cockatiel, resilience4j, tenacity, Polly, service mesh outlier detection.

### `code_quality_metrics` Code Quality Metrics Dashboard

Tags: `application`, `debugging`, `env`, `skippable`.

Coverage, complexity or maintainability are measured over time.

Examples: Codecov, Coveralls, SonarQube, JaCoCo reports.

### `deployment_observability` Deployment Observability

Tags: `application`, `debugging`, `probe`.

The docs point to where a deploy's impact shows up, or deploys announce themselves to monitoring.

Examples: Grafana or Datadog dashboard links, deploy markers, Slack deploy notifications.

### `n_plus_one_detection` N+1 Query Detection

Tags: `application`, `debugging`, `probe`, `skippable`.

Code that talks to a database has N+1 query detection.

Examples: bullet, nplusone, DataLoader, query-count assertions.

### `profiling_instrumentation` Profiling Instrumentation

Tags: `application`, `debugging`, `judge`, `skippable`.

Performance can be profiled in production or development with checked-in setup.

Examples: Pyroscope, Datadog profiler, `clinic.js`, py-spy, JFR, pprof.

### `agents_md_validation` AGENTS.md Freshness Validation

Tags: `repository`, `docs`, `probe`.

Something checks that the agent instructions still match the code: link checks, doc tests or a job that runs the documented commands.

Examples: lychee, markdown-link-check, a CI job running AGENTS.md commands.

### `dast_scanning` DAST Scanning

Tags: `application`, `security`, `probe`, `skippable`.

A deployed web service is scanned while running, in CI against a test environment.

Examples: OWASP ZAP, Nuclei, StackHawk, Burp.

### `privacy_compliance` Privacy Compliance

Tags: `repository`, `security`, `judge`, `skippable`.

End-user data collection has consent, retention and deletion handling.

Examples: consent management, data retention policy, export and delete endpoints.

### `code_modularization` Code Modularization Enforcement

Tags: `application`, `style`, `probe`, `skippable`.

Module boundaries are enforced by tooling, so an agent cannot quietly import across layers.

Examples: dependency-cruiser, eslint-plugin-boundaries, import-linter, ArchUnit, Go internal/.

### `backlog_health` Backlog Health

Tags: `repository`, `task_discovery`, `env`, `skippable`.

Open issues have descriptive titles, labels and recent activity. Needs forge access.

Examples: gh issue list.

### `flaky_test_detection` Flaky Test Detection

Tags: `application`, `testing`, `env`, `skippable`.

Flaky tests are caught and managed through retries with tracking, quarantine or stability metrics.

Examples: pytest-rerunfailures, Playwright retries, Gradle test-retry, BuildPulse.

### `test_isolation` Test Isolation

Tags: `application`, `testing`, `probe`.

Tests run in parallel or random order without interfering, so hidden coupling shows up.

Examples: vitest or jest default parallelism, pytest-xdist, pytest-randomly, `t.Parallel()`, Testcontainers.

### `test_performance_tracking` Test Performance Tracking

Tags: `application`, `testing`, `probe`.

Test durations are recorded and kept, not just pass or fail.

Examples: pytest --durations, JUnit reports uploaded, test analytics platform.

Examples: Sentry GitHub integration, Sentry release action, error-to-issue automation.

### `cyclomatic_complexity` Cyclomatic Complexity

Tags: `application`, `style`, `probe`.

Code complexity is measured against a threshold.

Examples: ESLint complexity, ruff C901, radon, lizard, gocyclo, PMD, SonarQube.

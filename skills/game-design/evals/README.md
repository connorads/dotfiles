# Maintaining game-design

These are design-response trials, not evidence that a game is fun. The cases
exercise invention, diagnosis, concrete rule reasoning and scope control.

## Run the comparison

1. Use fresh sessions with the same model, settings, tools and response budget.
   Keep authoring history and unrelated memory out of each session. Each case
   needs a separate session; do not run a batch inside one conversation.
2. Compare three arms: the prompt alone; the prompt plus the sentence below;
   and the prompt with explicit access to this skill and its routed references.
   Give the skill arm an instruction to read the body, matching deliberate use.
3. Record full transcripts, skill/reference reads, outputs, model identity, usage,
   wall time and permission failures. An unavailable tool is not a design result.
4. Review outputs under shuffled labels against each case's assertions. Check
   rule coherence, specificity, intent and unwarranted claims, as well as whether
   the response produces a useful design recommendation. Read the transcripts
   for unnecessary work and reference routing.
5. Use cases 1-8 for drafting. Reserve cases 9-10 from wording revisions until
   validation. Compare creative quality with the user; a numerical checklist
   cannot certify originality, enjoyment or taste. Repeat failures after edits.

Ad-hoc comparison sentence:

> Design for the intended player experience. Be concrete and imaginative, learn
> from relevant references, and use focused playtests to check your assumptions
> without overbuilding.

Keep raw outputs, evidence ledgers and candidate snapshots outside the shipped
skill. Keep any playable prototypes with launch instructions for human review.

## Review limits

The engineering case checks that invoking the skill does not derail a specified
technical task. It is not a claim to validate every proposed optimisation.
The reference-inspired cases provide preferences, not verified mechanics of the
named games. If a response relies on additional factual claims, inspect its
sources separately.

When evaluating automated discovery in a new installation, add near-miss trigger
cases and verify actual loading. Explicit invocation trials do not measure
automatic trigger reliability.

# Screens and collections

## Start from the decision

Write the objects, facts and actions needed for one complete task. Put facts
used together in the same view. Default to an overview for choosing among
items, a detail view for inspecting one, or an editor for changing it. Use a
guided sequence when order, branching or unfamiliar decisions need guidance.

For a review task, give the evidence enough room to read beside its decision
controls. Treat the working information as the space budget's first claim.
Add navigation destinations and repeated metadata only when they support an
actual transition or comparison. Check the result with realistic content before
adding a larger shell.

**Example.** A repair coordinator needs the fault, access constraints and
available appointment together to assign a visit. Company settings do not need
the same prominence. At the tested width, the short fault description should
not require scrolling through several copies of the request's identity.

## Choose the collection structure

Establish the collection's volume, identifying fields, useful order and actual
actions before choosing cards or a table. Expose the fields used to distinguish
items or make a comparison. Add selection only for an actual selection task.

For repeated inspection, start with list and detail together where they fit.
Use a full detail view with a return path when detail needs the space. Inline
expansion suits comparing small details from several items. Retain useful list
context when moving between these arrangements.

Search and filters explain their scope and retain the active constraints.
Choose immediate filtering when the person explores visible results. Consider
an explicit Apply action when they compose several constraints or cannot see
the results while choosing. Test the choice with keyboard input, a slow result
and browser Back. Zero matches keeps the means to change the query.

## Make return behaviour deliberate

Identify what returning needs: query, filters, ordering, selected item, position
or an unfinished edit. Preserve the relevant state visibly and let it change.
Avoid making people rebuild their working set after every item.

Decide whether state belongs in a shareable location, private preference or
saved work from the product's capabilities. A view can preserve its position
without promising cross-device drafts. Open directly, navigate away and return
to check the promise actually made.

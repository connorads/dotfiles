# Workflows and actions

## Choose the repeated-work pattern

Keep common tools available for a repeated task. Give occasional tasks enough
local explanation to complete without recall. Compare several attempts, not
only the first screen.

For a short repeated entry, start with a persistent add form and a visible
collection. Use a guided item flow when conditional questions need explanation
or prescribed order. Inline repeated rows suit frequent, simple batch entry.
Justify each question by its present use before choosing how to display it.

When work spans interruptions, show meaningful task status and a way to resume
from actual saved state. Identify the storage and completion rules first.
When an earlier answer changes a branch, reconcile dependent answers and
completion state so the final review describes what will actually be submitted.
Retain still-valid work after errors.

## Treat uploads as a collection

After files are selected, give the collection and its issues priority over the
empty-state upload invitation. Condense that setup area and keep an Add files
control available across separate selections. Show inspection, state and
recovery beside each file; one failure does not erase successful files. Let the
person remove mistaken choices, then finish with a clear account of what was
accepted. A temporary toast cannot be the only record.

Distinguish selected, processing, accepted and committed where those are real
stages. Choose whether unresolved files block completion or can be excluded
from the operation. State that choice beside the completion action. Retry only
when another attempt can change the result; permanent rejection needs a reason
and a different way forward. A file picker remains usable without drag-and-drop.

## Match feedback to the operation

For a substantial action, establish its targets, scope, progress and possible
recovery from actual capabilities. Put status beside the affected work so the
person can decide what to do next after a notification disappears.

Use preview when the task involves comparing possible outcomes before applying
a change. Cancellation concerns a running operation; undo concerns a completed
one. Neither promises restoration unless the operation supports it. For a
frequent reversible action, consider recovery instead of repeated confirmation.
For irreversible consequences, make the consequence explicit before commitment.

**Example.** A file renamer previews current and proposed names and collisions.
Changing the selection updates the preview and action count. Its cancellation
message describes any changes already applied; its undo reverses the named batch
only if that capability exists.
